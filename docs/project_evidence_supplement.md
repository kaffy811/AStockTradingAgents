### 建议补测方案（待执行）

1. 固定同一份代码、四只股票的数据快照、Prompt、实际请求模型 ID 和参数。串行与并行仅改变调度方式；综合汇总步骤也保持相同。
2. 将完整报告时间定义为“请求进入后端至完整响应就绪”，另记数据获取、四路 Agent、综合汇总的耗时。流式首字时间单独记录。
3. 区分冷缓存与热缓存，使用隔离的测试缓存；逐次验证缓存状态。热缓存预热不计入正式样本，禁止命中最终报告结果缓存来代替实际生成。
4. 每种缓存条件下，四只股票各做 5 组串行/并行配对，交替执行顺序，单个用户请求并发数固定为 1。共 40 组配对、80 次正式请求；预热另计。**这是计划次数，尚未执行。**
5. 留存每次结果、四路 Agent 状态、重试/失败/降级、输入输出 token、原始耗时。失败样本照常保留并单独汇总，不能只统计成功且最快的请求。
6. 分别报告各股票与各缓存条件的样本数、中位数、范围及配对加速比。该样本量下 P95 仅作探索性统计，附原始记录。

建议原始记录字段：`tested_at, git_sha, environment, stock, pair_id, execution_mode, cache_state, model_id, prompt_hash, data_snapshot_hash, input_tokens, output_tokens, data_ms, technical_ms, fundamental_ms, peer_ms, news_ms, synthesis_ms, total_ms, status, retry_count, degraded`。密钥和访问令牌不进入记录。

## 2. 一个成功案例：宁德时代动态同行分析恢复

**用户任务：** 输入 CN/300750，生成包含同行对比的四维研究报告。

**原始问题：** 早期缺少行业映射，返回 `peer_source="none"`，原因是 `industry mapping not found`，同行对比无法正常展开。

**我采取的措施：** 补充申万一级行业映射；无手工同行配置时，按照同一行业的 Hot Score 获取动态同行；保留手工配置优先级。Hot Score 基于成交额和涨跌幅，我在报告中明确说明它代表市场关注度，不代表基本面质量。

**已有结果：** 2026-05-29 的 Smoke Report 记录：300750 映射至电力设备（801730），`peer_source` 变为 `dynamic_hot`，返回阳光电源、锦浪科技等同行；四个 Agent 状态均为 success，四个报告维度完整，且保留估值字段缺失提示。

**成功边界：** 这个案例证明了行业映射、同行发现和报告生成流程恢复；未做同行选择质量的专家评审，也没有证明报告的所有财务结论均准确。

**可直接使用的面试表述：**

> 一个比较具体的成功案例是宁德时代的同行分析。早期因为缺少行业映射，系统无法找到同行。我编写行业数据导入逻辑，补充申万一级行业映射，再实现按同行业市场热度发现动态同行的规则，恢复了报告的同行对比部分。我还保留了手工配置优先级，并在报告中标注热度不代表基本面质量。这个案例验证的是数据覆盖与分析流程的改善。

依据：[Smoke Report 的 CN/300750 用例](mvp_smoke_test_report.md)、[行业导入脚本](../backend/scripts/import_industry_map.py)、[动态同行服务](../backend/app/services/dynamic_peer_discovery_service.py)。该案例属于实习期间。

## 3. 一个不理想的案例：经营现金流问答答偏

**样本：** 友发集团 601686，2024 年第三季度报告，`report_id=2`，问题 ID 为 `2024_q3_cashflow`。产物随 `e6f702d`（2026-07-12）入库，属于实习期间。

**用户问题：** “本期经营现金流情况如何？”

**实际回答片段：** “二、投资活动产生的现金流量：；投资活动现金流入小计 1,831,679,876.43 1,996,077,395.59”。

**为什么不理想：** 用户问经营活动，回答却突出投资活动，且未给出正确的经营活动现金流结论。引用中虽然包含现金流量表与经营活动的片段，但没有保证最终回答使用正确的财务科目。

**现有证据与原因判断：**

- 产物显示首条引用来自第 12–13 页的投资现金流片段，另一条来自第 11–12 页的经营活动片段；回答选择存在语义错配。
- 这轮索引产物记录的 embedding 为 `company-v2-hash-keyword-v1`，属于哈希/关键词方案，不是训练过的语义 Embedding 模型；不能把这轮结果归因于 BGE 或 DeepSeek 的回答能力。
- 从样本可以判断“检索到相关页面”没有保证“答对所问科目”。是否由表格切分、排序或答案片段选择各自贡献了多少错误，未做消融定位。

**为什么脚本仍判定通过：** 原脚本只要 `status="answered"` 且存在引用，就认为这类题目满足预期；`citation_page_correct` 也只检查引用列表非空。它没有逐页核验引用，没有匹配正确答案，也没有区分经营、投资和筹资现金流。

**需要纠正的评估口径：**

| 原产物字段 | 脚本实际统计的内容 | 对外可说的内容 |
| --- | --- | --- |
| `retrieval_hit_rate=1.0` | 6 个预期可回答问题均返回 `answered` | 6 个可回答样本均返回回答状态；不能称为人工标注的检索命中率 |
| `citation_page_accuracy=1.0` | 6 个样本均存在引用 | 引用存在率 6/6；页码准确率未做核验 |
| `cross_report_leakage=0` | 8 个样本中程序未标记跨报告串用 | 这组固定样本未检测到跨报告串用 |
| 两个拒答样本 | 错误年份、季度报告问全年均返回 `insufficient_evidence` | 两个边界拒答检查通过 |

这轮共 8 题、3 份报告（2024 年年报、2024 年三季报、2023 年年报）；不能称为 8 份财报或整体回答准确率 100%。引用页码准确性、标准检索相关性、完整答案事实准确性评估：未做。

**建议改进（本次未改代码、未验证修复）：** 标注每题正确财务科目、期间、标准答案和相关 chunk/页码；检索和答案选择增加经营/投资/筹资科目区分；对表格保留列名、单位和期间；证据不足时拒答。然后分别评估相关证据是否召回、排序是否合理、答案数值与科目是否正确。

**可直接使用的面试表述：**

> 一个失败案例是经营现金流问答。系统能返回财报引用，但答案突出的是投资现金流。复查后发现，原来的自动检查只验证有无回答和引用，所以通过也不代表答对。这让我意识到，需要把链路检查与内容质量评估分开，并补充财务科目、期间、数值和引用依据的标注。当前材料不将这组检查表述为答案准确率 100%。

依据：[原始问答产物](../backend/docs/artifacts/company_v2_601686_multi_report_rag_eval_phase6te3.json)、[索引产物](../backend/docs/artifacts/company_v2_601686_multi_report_index_phase6te3.json)、[评估脚本](../backend/scripts/company_v2_multi_report_rag_eval.py)。
